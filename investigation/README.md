# Emulating a Hörmann UAP1 on ESP32 — field notes

A **practical, condensed** guide for anyone walking the same path: making an ESP32 (the
`hormann_hcp1` component) act as a **UAP1** on a Hörmann operator's HCP1 bus, in order to
**read** the door state **and command** it.

Validated target: **WeAct CAN485 DevBoard** (ESP32 + **isolated** CA-IS2092A RS485 transceiver).
Result: **full UAP1 emulator** — monitoring (door/light/error/venting) **and** command
(impulse / open / close / light / venting / stop). **The door opens.** ✅

> The full chronological log (every session, dead ends included) is in
> [`../INVESTIGATION.md`](../INVESTIGATION.md). This file is the "what you need to know" version
> so you don't lose the days we lost.

---

## TL;DR — the two locks that cost the most

1. **Dead RX on an ISOLATED transceiver** → you must **physically swap A/B** (+ `ab_inverted: true`).
2. **Command ignored (the master scans but never registers you)** → the **sync break is too short**.

If you only read this: apply those two fixes and test.

---

## The bus & the hardware

- **HCP1 bus** = RS485 **19200 8N1**, half-duplex. Operator connector (model-dependent):
  `pin 2 = 24VDC`, `pin 3 = GND`, `pin 5 = RS485 DATA- (B)`, `pin 6 = RS485 DATA+ (A)`.
- **WeAct CAN485**: **isolated CA-IS2092A** transceiver (integrated isolated DC-DC, `VDD5V_ISO`
  generated by the chip). RS485: `DI(TX)=GPIO22`, `RO(RX)=GPIO21`, `DE=GPIO17`. WS2812=GPIO4, KEY=GPIO0.
- **Board switches**: **PUPD = OFF**, 120 Ω termination = OFF (the master already biases & terminates).

## Lock 1 — RX: `0 valid, 0 junk, 0 breaks` on the isolated board

**Symptom**: the sniffer sees **nothing** (not even breaks), while a **non-isolated** module
(SP3485/ST485) wired to the **same wires** decodes perfectly (~280 frames, valid CRCs).

**Diagnosis** (on a scope, ref. GND_ISO): this Hörmann bus drives **asymmetrically** —
**DATA+ (pin 6) does the full swing** (−0.4 → +3.2 V), **DATA- (pin 5) stays near GND**.
The differential exists (carried by A); a non-isolated transceiver decodes it. But the
**isolated CA-IS2092A has an aggressive internal fail-safe** that reads the weak "space" level
(−0.4 V) as **permanent idle** → its RO output stays stuck → 0/0/0.

**Solution**:
- **Physically swap A and B** at the board input: `pin 6 (DATA+) → terminal B-`,
  `pin 5 (DATA-) → terminal A+`. This puts the strong swing on the "space" side → the receiver locks.
- RO is then **logically inverted** → compensate with **`ab_inverted: true`** (inverts RX **and**
  TX together — it's a single differential pair).

> A **non-isolated** transceiver (ST485/SP3485, like stephan192) does **not** have this problem:
> it decodes the bus in **normal polarity** (`ab_inverted: false`), no swap. The trap is specific
> to the fail-safe of **isolated** transceivers.

**Diagnostic tip**: the measurement that settles "wiring vs polarity vs HW" = scope **A+ vs GND**
then **B- vs GND**. If **only one line toggles**, the differential is "half" → that's the
asymmetric case above.

## Lock 2 — Command: the master scans 0x28 in a loop but never escalates

**Symptom**: the master **scans** our address (`28:..:01:..`, often `+N identical` = it
**hammers** it), we **reply** (the witness sees a clean `OUR-SCANRESP`), **but** it never moves
to `status_request` (0x20) → we're **not registered** → `impulse` ignored.

**What was ALREADY correct** (checked byte-for-byte against a real UAP1 trace **and** stephan192):
scan response `80:12:14:28`, status response `80:..:29:00:10`, counter, **reply timing 3840 µs**,
5 V drive. **The protocol was not the issue.**

**THE cause**: the **sync break** (the leading `0x00` before each frame) was **2× too short**.

| source | break (low level) | bits @19200 | works? |
|---|---|---|---|
| **real UAP1** (measured on Saleae trace) | **~920 µs** | **~18 bits** | ref |
| **hgdo** (`0x00` @ 9600 7N1) | ~833 µs | ~16 bits | ✅ |
| **our old code** (`0x00` @ 19200) | **~470 µs** | **~9 bits** | ❌ |

The **strict** master did not recognize the start of our frame → didn't **frame** it → didn't
register us. (A tolerant receiver like our own witness did decode — hence the confusion.)

**Solution** (in `send_frame`, hgdo's method): emit the break `0x00` at **half baud (9600)** =
~937 µs low (~18 bits @19200), **then switch back to 19200** for the frame. `uart_set_baudrate`
is fast (plain register writes — the "40 ms" myth is false).

**Immediate result**: the master **escalates** to `status_request` every ~100 ms,
`impulse` → status `80:..:29:**04**:10` (data 0x1004) → **the door opens**.

## ⚠️ Dead ends — do NOT waste time on these

- **µs-level timing is NOT critical.** `hgdo` (ESP8266 + SoftwareSerial) replies with a
  **millisecond** delay (`millis()`, `TX_DELAY = 3 ms`, ms jitter) and drives the door.
  No need for a dedicated MCU / cycle-precise timing. ~3.8 ms ±1 ms is enough.
- **PUPD: leave it OFF.** The bias added by the board **disturbs the bus**. Its impact is a
  **spectrum** depending on the bus/your position: sometimes it kills reception entirely (even a
  passive witness goes blind); sometimes it leaves **RX working but silently blocks the command**
  — it weakens our TX drive just enough that the master never registers our reply (state reads
  fine, but no command). **Field case**: identical code/board, RX OK on both, one board couldn't
  command → its PUPD switch was ON. So: **PUPD = OFF, full stop.** The board's **120 Ω** is
  **neutral on RX** but also loads the TX drive — keep it OFF too on the Hörmann bus.
- **Software inversion alone is not enough** on the isolated part: `ab_inverted` only inverts the
  UART **after** the chip. The chip's fail-safe acts on the **analog** side → you need the
  **physical swap**.
- **The startup serial announce is NOT required.** A real UAP1 broadcasts its serial number at
  boot, but **stephan192 does not implement it** and still commands. No need to reproduce it.
- **Beware of your own witness.** Ours was **transmitting** its own scan response (forgotten
  `listen_only`) and **polluting the bus** → you need a **truly passive** oracle (`listen_only: true`).
- **The latency seen by the oracle is skewed** when the master hammers the scan (`+N identical`):
  measure from the **first** request of the burst, not the last (see the fix in the component).

## Method & tools (in this folder)

- **`sniffer: true`** (component option): logs the bus frames categorized (`SCAN->us`,
  `STATUS_REQ->us`, `BCAST`, `OUR-SCANRESP`, `OUR-STATUSRESP`) plus an
  `N valid / N junk / N breaks` heartbeat. First reflex to see what's happening.
- **Witness oracle**: a 2nd board in **`listen_only: true`** (never transmits) that observes
  everything and flags **our** replies (`OUR-SCANRESP<<<`) + the real latency. Essential to
  confirm our TX reaches the bus cleanly **without** being a participant ourselves.
- **[`track_analyse/decode_uart.py`](track_analyse/decode_uart.py)**: decodes a **logic capture
  (Saleae)** CSV export into **Hörmann frames** (19200 8N1), TX and RX separately, with timing
  and break durations. This is what gave us the **~920 µs break** and confirmed our frames were
  byte-identical to a real UAP1.
  ```bash
  python3 investigation/track_analyse/decode_uart.py investigation/track_analyse/UAP1-startup.csv
  ```
- **[`track_analyse/UAP1-startup.csv`](track_analyse/)**: Saleae capture of a **real UAP1 boot**
  (reference to compare scan/status/break/timing). Source: bouni's traces.

## The working config (excerpt from `example_can485.yaml`)

```yaml
# Bus -> board wiring: pin6 DATA+ -> terminal B-, pin5 DATA- -> terminal A+ (SWAPPED), pin3 GND -> Mass.
# Board switches: PUPD OFF, 120 Ω OFF.
hormann_hcp1:
  id: hormann
  uart_num: 1
  tx_pin: GPIO22       # DI
  rx_pin: GPIO21       # RO
  de_pin: GPIO17       # DE (active-high)
  ab_inverted: true    # A/B physically swapped -> software re-inversion RX+TX
  reply_delay_us: 3800 # reply latency tuned to a real UAP1 (~3.84 ms)
  sniffer: false       # true = debug
```
